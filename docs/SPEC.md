# 제품 스펙 (SDD)과 수용 기준 — 검토용 초안

> 강의 4 산출물. 문제와 증거는 [PROBLEM.md](PROBLEM.md), 도메인 대표어는 [ontology.yaml](ontology.yaml)을 정본으로 삼는다. 이 문서의 기능 경계·수용 기준은 팀 확정 전 제안이다.

## 1. 문제

수학 연계문항 제작·검토자는 원문의 핵심 풀이 의도를 유지하면서 후보 문항의 조건과 풀이가 성립하는지 확인하기 위해 수정과 재검토를 반복한다. 자세한 근거와 반증 조건은 [문제 정의서](PROBLEM.md)에 둔다.

## 2. 타깃 사용자

- **1차 사용자:** 원본문항을 바탕으로 연계문항을 만들고 검토하는 수학 문항 제작자와 학원 수학 강사. (로그 1~10)
- **현재 비대상:** 학생용 문제 풀이 서비스, 비수학 문항 제작, 문항 판매·정산 업무.

## 3. 핵심 기능 — 한 문장

원본문항과 풀이에서 `SolutionIdea`를 구조화하고, 그 풀이 의도를 유지하는 연계 후보 문항과 풀이를 만든 뒤, 조건·수학적 성립·교육과정 문제를 `ReviewResult`로 드러내어 제작자의 검수를 돕는다.

## 4. 범위

**포함(제안)**

- 원본문항과 제공된 풀이에서 `SolutionIdea.concept`와 `SolutionIdea.mechanism` 추출. 현재 산출물: `src/aleph/schemas/solution_idea.schema.json`, `src/aleph/prompts/parse_query.md`.
- `GenerationRequest`의 사용 목적과 목표 난도를 받아 `Question(CANDIDATE)` 및 풀이 생성. 후보 생성 방식은 강의 6 아키텍처에서 정한다.
- 후보의 조건 누락·경계값·적용 조건·수학적 성립과 교육과정 문제를 검토하고 `ReviewResult` 및 이유를 제시. (로그 3, 4, 7, 8, 9, 10)
- 제작자가 후보와 검토 근거를 보고 사용·수정·보류를 결정하는 흐름. 자동 게시·최종 채택은 범위 밖이다.

**비포함**

- 결제·판매·정산, PDF·이미지의 수식 복원, 공간도형 자동 작도, 비수학 문항 생성.
- 실제 학생 풀이 데이터 없이 정답률이나 체감 난도를 확정하는 기능.
- 모든 수학 영역에서 전문가 검수 없이 상용 품질을 보장한다는 주장.

비포함 항목은 [온톨로지의 범위 밖](ontology.yaml)과 맞춘다.

## 5. 인터페이스 — 논리 계약 초안

전송 방식(HTTP, CLI, 내부 함수)은 미정이다. 아래는 **단계 간 입력·출력의 모양**이며 구현된 API가 아니다.

| 단계 | 입력 | 출력 | 현재 상태 |
|---|---|---|---|
| 풀이 아이디어 추출 | 원본문항의 본문·풀이 | `SolutionIdea {concept, mechanism, transferable?}` | 스키마·프롬프트 초안 있음. 실행 코드 없음. |
| 후보 생성 | `Question(SOURCE)`, `GenerationRequest {intended_use}`, 목표 `DifficultyProfile`, `SolutionIdea` | `Question(CANDIDATE)`의 문항 본문·풀이 | 설계 제안. 생성 방법 미정. |
| 후보 검토 | 원본문항, 후보 문항·풀이, 보존할 `SolutionIdea` | `ReviewResult {validity_issue, curriculum_issue, verdict, reason, reviewer_type}`와 근거 | 설계 제안. 자동 판정 범위 미정. |

**계약을 확정하기 전의 빈칸:** 현재 `Question` 온톨로지에는 문항 본문과 안정적인 식별자 속성이 없다. 원문·후보를 입출력으로 주고받고 `derived_from` 관계를 추적하려면 팀이 필드명과 출처를 정해 온톨로지·후속 스키마에 반영해야 한다. `ReviewResult.verdict`의 `[USE, REVISE, HOLD]`와 검수 장부의 판정값 간 대응도 아직 미정이다. 문항 생성 알고리즘은 이 스펙에서 고정하지 않는다.

## 6. 수용 기준 — 팀 검토용

각 AC의 조건 유형을 표시했다. 강의 5에서 사람이 확정할 골든 케이스를 `tests/harness/golden_cases.yaml`에 두고 AC 번호와 연결한다. 현재 파일은 없으며 아래는 **테스트 가능한 기준 후보**다.

| 번호 | 유형 | 수용 기준 | 판정 예시 |
|---|---|---|---|
| AC1 | 이벤트 기반 | 원본문항과 풀이에서 핵심 개념·풀이 행동을 추출할 때, Aleph는 `SolutionIdea` 스키마에 맞는 JSON 객체 하나를 출력한다. | `concept`, `mechanism` 키가 있고 스키마 밖 키가 없으며 JSON 검증을 통과한다. |
| AC2 | 예외 대응 | 입력에 핵심 풀이를 판단할 근거가 없을 때, Aleph는 `mechanism`을 `null`로 두고 후보 생성을 진행하지 않으며 필요한 풀이 정보를 요청한다. | 풀이 없는 입력에서 구체적 풀이 단계를 지어내거나 생성으로 넘어가면 실패한다. |
| AC3 | 상시 적용 | Aleph가 후보 문항을 제시할 때마다, 원본문항과 후보의 대응 관계 및 각각의 핵심 풀이 메커니즘을 제시하고, 보존 여부를 `ReviewResult.reason`에 기록한다. | 출처 연결 또는 두 메커니즘 중 하나가 빠지면 실패한다. 전문가가 풀이를 확인해 보존되지 않았다고 표시한 골든 케이스를 `USE`로 판정해도 실패한다. |
| AC4 | 예외 대응 | 후보에 골든 케이스로 정의된 반례·정의역 누락·경계값 오류가 발견되면, Aleph는 `ReviewResult.validity_issue=true`를 기록하고 `USE` 판정을 내리지 않는다. | 로그 3, 4, 6, 7, 8, 10 유형의 사례에서 `USE`가 나오면 실패한다. 케이스별 기대값은 사람이 확정한다. |
| AC5 | 예외 대응 | 후보의 풀이가 사전 정의한 교육과정 범위를 벗어나면, Aleph는 `ReviewResult.curriculum_issue=true`를 기록하고 `USE` 판정을 내리지 않는다. | 로그 9 유형의 교육과정 이탈 케이스에서 `USE`가 나오면 실패한다. 범위의 기준 자료는 팀이 확정한다. |
| AC6 | 상시 적용 | 실제 학생 풀이 데이터가 없으면, Aleph는 `DifficultyProfile.student_verified=true`나 실측 정답률이라고 표현한 값을 만들지 않는다. | 학생 풀이 데이터가 없는 케이스에 검증됨 표시나 실측 수치가 있으면 실패한다. |
| AC7 | 이벤트 기반 | 후보 생성과 검토가 끝나면, Aleph는 후보 문항·풀이와 `ReviewResult.verdict`, `reason`을 함께 제시한다. | 후보만 있고 풀이 또는 검토 이유가 없으면 실패한다. |

AC4·AC5는 결함을 **발견했을 때의 처리 규칙**을 판정한다. 결함을 얼마나 잘 찾아내는지는 별도 전문가 라벨 데이터와 평가 지표가 있어야 검증할 수 있다. `REVISE`와 `HOLD`를 어느 상황에 쓰는지, 독립 풀이로 무엇을 확인할지 팀이 정해야 한다.

## 팀 확정이 필요한 결정

1. 1차 사용자와 비대상, 후보 생성 범위.
2. `Question` 본문·식별자 필드 및 `ReviewResult.verdict` 매핑.
3. 교육과정 기준 자료, 수학적 검증 절차와 사람이 최종 판정하는 지점.
4. AC별 골든 케이스와 기대값. 이 초안의 AC를 팀이 승인하기 전까지 완료 기준으로 간주하지 않는다.
