## A. 인터뷰 프로토콜

> **원칙**: 과거 행동만 묻는다. 미래·가정·유도 질문을 쓰지 않는다.
> 인터뷰가 끝나도 상대는 우리 아이디어를 몰라야 한다.

### 대상 (누구를, 왜 — 행동 조건을 넣어서)

입시업체에서 연계문항 초안을 **직접 제작하고**, 이후 검토 결과와 수정·채택 여부까지
설명할 수 있는 사람. 직접 수행한 제작 과정과 판단을 구체적인 사건으로 재구성하기
위해 이들을 대상으로 한다.

> **모집 조건**: 수정 경험을 필수조건으로 걸지 않는다. 초안이 그대로 채택된 사례도
> 포함해 수정 부담이 과대평가되지 않게 한다.

### 가설 (틀릴 수 있는 문장으로)

> 연계문항 제작에서는 아이디어 구상보다, **목표 난도에 맞추기 위한 수정**과
> **기출·타사 문항의 중복 확인**에 더 많은 작업 시간이 든다.
> 특히 예상 난도와 실제 학생들의 풀이 결과가 어긋났을 때, 원인을 파악하고
> 난도를 다시 조정하는 과정에서 수정이 반복된다.

**반증 조건** — 아래 중 하나라도 나오면 가설의 해당 부분이 틀린 것이다.

| 확인할 것 | 가설이 틀리는 경우 |
| :--- | :--- |
| 아이디어 구상 시간 vs 수정 시간 | 구상이 더 오래 걸림 |
| 난도 조정 시간 | 거의 들지 않음 |
| 중복 확인 시간 | 거의 들지 않음 |
| 예상↔실제 난도 차이 | 대체로 일치, 재조정 없음 |

### 자료 분석 후 수정한 가설

실제 로그 1~10에서는 중복 확인이 많은 시간을 차지한다기보다 기억에 의존하거나 일부 보유 자료만
대조하는 경우가 확인됐다. 반면 작업물 관찰에서는 생성 후보 33건 중 24건이 한 번에 `ok`를 받지
못했고, 변형부족·과변형·후보중복·타당성결함이 반복됐다. 따라서 핵심 가설을 다음과 같이
수정한다.

> 연계문항 제작·검토의 주요 비용은 원문의 **핵심 풀이 메커니즘은 보존하면서 조건과 표현은
> 충분히 바뀐 타당한 후보**를 만드는 데 있다. 이 균형에 실패하면 변형부족·과변형·후보중복·
> 타당성결함으로 반려되고 조건 수정과 재검토가 반복된다. (로그 1~10 / 관찰 1)

**수정 가설의 반증 조건**

- 새 후보 20건 중 70% 이상이 첫 검수에서 `ok`를 받으면 반복 검토가 핵심 문제라는 가설을 기각한다.
- 수정 대상 후보의 중앙 수정 횟수가 1회 이하라면 수정 반복이 주요 비용이라는 가설을 기각한다.
- 실패의 대부분이 풀이 메커니즘·변형 균형과 무관한 편집 문제라면 현재 문제 정의를 기각한다.

### 질문 5개

> 하나의 사건을 따라간다. 질문마다 의도를 병기한다.
> `●` 기본으로 묻는 후속 / `○` 답변에 따라 선택해서 묻는 후속.
> 후속을 순서대로 모두 읽지 않는다. 이미 설명한 부분은 건너뛰고 빠진 정보만 묻는다.

**Q1. 최근에 직접 만드신 연계문항 하나를 처음부터 끝까지 얘기해 주세요.**
— 과거의 구체적 사건 하나로 고정. "보통"이 아니라 "그때"의 행동.

- ● 언제였고, 어떤 과목·유형이었어요?
- ● 그 문항을 만드는 과정에서 직접 담당하신 부분은 어디까지였어요?

**Q2. 그 문항은 처음에 어느 정도 난도로 만들려고 하셨어요?**
— 목표 난도와 판단 근거, 구상·작성에 든 제작 비용.

- ● 어떤 수준의 학생들이 푸는 것을 기준으로 잡으셨어요? 목표 정답률도 있었나요?
- ● 초안을 완성했을 때 의도한 난도가 나왔다고 보셨어요? 무엇을 근거로 판단하셨어요?
- ● 그 문항의 아이디어는 어떻게 떠올리셨어요?
- ● 당시 어떤 문항·자료나 도구를 펼쳐 놓고 작업하셨어요?
- ● 아이디어를 정하는 데 실제로 작업한 시간은요? 정한 뒤 초안 작성에는요?

**Q3. 그 문항을 실제로 풀게 하거나 검토받았을 때, 결과는 처음 예상과 비교해 어땠어요?**
— 예상과 실제의 차이, 확인 근거, 수정 비용. *수정했다는 전제를 두지 않는다.*

- ● 어떤 자료나 의견으로 결과를 확인하셨어요?
- ○ 학생 정답률을 확인했다면, 예상 수치와 실제 수치는 각각 어느 정도였어요?
- ○ 어떤 학생들이 몇 명 정도, 어떤 조건에서 푼 결과였어요?
- ○ 예상과 차이가 있었다면 무엇 때문이라고 보셨어요? 그 이유는 어떻게 알아보셨어요?
- ● 그 결과를 확인한 뒤 어떻게 하셨어요? 수정했다면 무엇을 왜 바꾸셨어요?
- ○ 몇 번 수정했고 각각 얼마나 걸렸어요? 직접 작업한 시간과 기다린 기간은 나눠서요.

**Q4. 그 문항이 기출이나 다른 업체 문항과 겹치는지 확인하는 과정이 있었나요?**
— 확인 여부·담당자·도구·비용과 우회로. *확인했다는 전제를 두지 않는다.*

- ○ 있었다면 누가, 어떤 자료와 방법으로 확인했어요?
- ○ 그 확인 작업에는 얼마나 걸렸어요?
- ○ 확인 과정에서 막히거나 판단하기 어려웠던 부분이 있었나요? 어떻게 처리하셨어요?

**Q5. 그 문항은 최종적으로 어떻게 처리됐어요?**
— 채택·보류·폐기의 실제 결과와 판단 기준, 난도 조정 후 재확인 여부.

- ● 누가 어떤 이유로 그렇게 결정했어요?
- ○ 수정한 경우, 고친 뒤의 난도는 다시 확인하셨나요? 어떤 방법으로 했고 결과는 어땠어요?
- ○ 최종본이 있다면, 초안과 비교해 달라진 점이 있나요?
- ● 당시 파일이나 피드백 기록을 함께 보며 설명해 주실 수 있을까요?

> ※ 실제 자료를 확인한 내용은 [C. 워크플로 관찰 기록](#c-워크플로-관찰-기록)으로 연결한다.

### 기록 원칙

> B절 로그를 작성할 때 적용한다.

**① 인터뷰 태도**
- 인터뷰가 끝날 때까지 우리 팀의 해결책을 설명하지 않는다.

**② 편향 방지**
- 예상과 결과가 일치했거나, 수정·중복 확인을 하지 않은 사례도 **그대로 기록한다.**

**③ 난도는 네 층으로 구분한다**

| 층 | 무엇인가 |
| :--- | :--- |
| 목표 난도 | 제작 전에 정한 기준 |
| 제작자 예상 난도 | 초안 완성 시점의 본인 판단 |
| 검토자 평가 | 검수자의 의견 |
| 실제 학생 정답률 | 측정된 수치 |

- 정답률 자료가 없으면 **검토 의견만으로 실제 정답률을 추정하지 않는다.**
- 풀이 결과를 **알게 된 시점**을 기록한다. 최종본 확정 이후에 알았다면, 해당 문항을
  수정했는지 / 다음 문항 제작에 반영했는지 구분한다.

**④ 시간 기록**
- 응답자가 말한 소요 시간은 **'진술'로 기록한다.** 기록과 비교할 때는 같은 항목끼리만
  비교하고, **파일 수정 시각을 실제 작업시간으로 확정하지 않는다.**
- **직접 작업시간**과 **대기로 늘어난 전체 기간**을 구분한다.
- **난도 조정 / 그 밖의 수정 / 중복 확인**에 든 시간을 각각 구분한다.

**⑤ 역할 구분**
- 제작자 본인이 한 일과 별도 검수자가 한 일을 구분해서 기록한다.

## B. 인터뷰 로그

> 여기 매기는 **# 번호가 곧 로그 번호**다. 온톨로지 `evidence:`가 이 번호를 가리킨다.
> - 인용은 요약이 아니라 **들은 말 그대로** 적는다.
> - 한 로그가 여러 페인을 낳아도 된다. 억지로 1:1로 나누지 않는다.
> - 태그는 요약이 아니라 **색인**이다. 태그 → 로그 번호 → 인용 원문으로 돌아갈 수 있어야 한다.
> - **우리 가설을 흔드는 로그도 지우지 않는다.**

> **출처 구분**: `로그 1`~`로그 10`은 모두 실제 사람에게 받은 인터뷰다. 이 중 `로그 3`~`로그 10`은
> 응답 내용을 AI로 문장 정리하고 CSV 형식으로 구조화한 기록이며, 인터뷰 내용과 역할·작업 경험은
> 실존 응답자의 답변이라는 사실을 자료 제공자가 2026-09-23에 확인했다. 원본 CSV에 남아 있던
> `AI_GENERATED_SIMULATION`과 시뮬레이션 관련 문구는 잘못 입력된 정리 메타데이터로 확인되어
> 인터뷰 출처 판정에 사용하지 않는다. 로그 3~10의 수집일은 2026-09-15로 확인했다.
> `A01`~`A08`은 `feedback_ledger.yaml`에서 확인한 실제 과거 검수 기록을 재구성한 작업물 기반 사례다.
> 검수 주체가 사람인지 여부는 이 파일만으로 확정하지 않으며, 인터뷰 수에는 포함하지 않는다.

### 도출된 페인 (누적)

> 각 항목에 **범주와 로그 번호 필수.**
> 범주: `[문제 / 목표 / 우회로 / 제약 / 실패 유형]`
> 범주에 따라 온톨로지에서 가는 곳이 다르다 — 제약은 속성과 절대 규칙으로,
> 우회로는 관계와 기능 요구로, 실패 유형은 수용 기준의 실패 조건으로.

1. **조건 수정의 연쇄 발생** [문제] — 한 오류를 수정하면 다른 반례나 풀이 경로가 발생해 수정이 반복됨 (로그 1, 2, 3, 4, 6, 7, 8, 10 / 사례 A03, A06, A08)
2. **핵심 보존과 충분한 변형 사이의 충돌** [문제] — 표면만 바꾸면 변형부족, 핵심까지 없애면 과변형으로 반려됨 (로그 3, 6, 7, 9, 10 / 사례 A01, A04, A07)
3. **제작 의도와 풀이 가능성의 충돌** [실패 유형] — 조건이 풀이에 쓰이지 않거나 의도하지 않은 풀이가 생김 (로그 1, 2, 3, 4, 6, 7, 8, 10 / 사례 A03, A06)
4. **교육과정 이탈 가능성** [제약, 실패 유형] — 검토 시 교육과정 밖 개념과 표현을 별도로 확인해야 함 (로그 1, 9 / 사례 A05)

### 인터뷰·작업물에서 도출한 문제 정의 후보

> **입시 수학 연계문항을 제작·검토하는 담당자가 원본문항의 핵심 풀이 메커니즘은 보존하면서
> 조건과 표현은 충분히 달라진 타당한 후보를 한 번에 만들지 못해, 변형부족·과변형·후보중복·

- **누가**: 입시 수학 연계문항 제작자와 검토자 (로그 1~10)
- **못 하는 것**: 핵심 풀이 메커니즘 보존과 충분한 변형을 동시에 만족하는 후보를 한 번에 만들기 (사례 A01, A04, A07)
- **대가**: 반복 검토·조건 수정·보류·폐기. 어려운 문항은 거의 일주일까지 이어짐 (로그 1 / 관찰 1)

## C. 워크플로 관찰 기록

> 인터뷰는 "말한 것", 관찰은 "한 것"이다. 응답자는 습관이 된 조작을 설명하지 못하므로
> 최근 사례를 그 자리에서 시연하게 하거나 화면 공유로 재현하게 한다.
> **"관찰 내용"에는 본 것(동작과 횟수)만, 해석은 "스펙 후보"에 적는다.** 섞으면 감상이 된다.

| 전환(Handoff) | 후보 파일명·`source_id`·`variant_tag`가 검수 장부 레코드로 이동. 전체 33건 중 24건이 `minor`·`revise`·`reject` | 생성 결과와 검증 결과를 같은 `problem_id`/후보 ID로 추적 |
| 우회로(Workaround) | 자유문장 피드백을 변형부족·과변형·후보중복·교육과정위반·타당성결함·조건미세조정으로 다시 분류 | 폐쇄형 `feedback_category`와 자유문장 `directive`를 함께 저장 |
| 멈칫(Hesitation) | 장부에는 작업 중 정지 시간과 수정 소요 시간이 기록되지 않아 관찰 불가 | 이후 실행에서 후보당 수정 횟수와 검토 경과시간을 별도 계측 |

- **진술과 관찰의 차이**: 실제 로그 1·2는 조건 수정과 의도 보존이 반복된다고 진술했다. 별도 프로젝트의 검수 장부에서도 33건 중 24건이 한 번에 `ok`를 받지 못했으나, 동일 응답자의 작업 기록은 아니므로 진술을 직접 검증한 것으로 간주하지 않는다.

## D. 핵심 Job Story

> 팀당 1개, 많아도 2개. 이 문장이 강의 4 스펙의 기능 시나리오로 넘어간다.

> 생성된 연계문항 후보를 검토할 때, 나는 원문의 핵심 풀이 메커니즘은 유지하면서 조건과 표현은 충분히 달라졌는지 확인하고 싶다. 그래서 반복 반려와 조건 수정 없이 채택 가능한 후보를 고를 수 있도록. (로그 1~10 / 관찰 1)

| 요소 | 내용 | 근거 |
| :--- | :--- | :--- |
| 상황(트리거) | 원본문항에서 생성된 연계 후보를 검토해 채택·수정·폐기를 결정해야 할 때 | 로그 1~10 / 관찰 1 |
| 기능적 Job | 핵심 풀이 메커니즘 보존, 충분한 표면 변형, 수학적 타당성, 교육과정 준수를 함께 판정 | 로그 1~10 / 사례 A01~A08 |
| 감정적 Job | 오류를 놓치지 않았다는 확신이 필요한지는 현재 자료에서 직접 확인되지 않음 | 미확인 — 추가 인터뷰 필요 |
| 사회적 Job | 좋은 제작자·검토자로 보이고 싶은지는 현재 자료에서 직접 확인되지 않음 | 미확인 — 추가 인터뷰 필요 |
| 현재 고용된 대안 | 직접 풀기, 타인 검토, AI 반복 검토, 기출 기억 비교, 자유문장 피드백 후 수동 수정 | 로그 1~10 / 관찰 1 |

### 전환의 네 힘

> **Pull은 반드시 `(가설)`로 표시한다.** 아직 없는 제품의 매력이라 인터뷰로 확인할 수 없다.
> 이것을 사실처럼 적는 순간 Mom Test가 무너진다.
> **Habit이 진짜 경쟁자다** — 기존 방식은 "실패가 없다"는 확신을 준다.

| 힘 | 내용 | 근거 |
| :--- | :--- | :--- |
| Push (기존 대안의 불만) | 수정이 연쇄적으로 발생하고, 검수 장부 33건 중 24건이 한 번에 통과하지 못함 | 로그 1 / 관찰 1 |
| Pull (새 해결책의 매력) | 핵심 메커니즘과 반드시 바꿀 표면 요소를 분리하고 자동 검증하는 파이프라인 | **(가설)** |
| Anxiety (새 해결책의 불안) | AI가 교육과정 밖 풀이를 쓰거나 의도하지 않은 풀이와 성립 오류를 놓칠 수 있음 | 로그 1, 2, 4, 7, 10 |
| Habit (관성) | 사람이 직접 풀고, 타인·AI에 반복 검토를 맡기며, 기출 중복은 기억과 보유 자료에 의존 | 로그 1~10 |

### 온톨로지로 되쓰기 검증

> Job Story를 온톨로지 어휘만으로 다시 쓸 수 있어야 한다.
> 한 요소라도 옮겨지지 않으면 온톨로지에 빈 곳이 있는 것이다.

`Question` → `ProblemFacts` → `ProblemSemantics` → `DonorCard` → `Question` → `ValidationResult`
